# AI 信息雷达产品需求文档（PRD）

> 状态：规划基线｜当前主要用户：AI 应用开发者｜产品阶段：V0.x

## 1. 产品目标

让用户第二天打开应用时，在不等待采集和 AI 生成的情况下，看到前一天完整自然日内最值得关注、来源可追溯、低重复的 AI 事件日报；同时可以查看今天仍在更新的实时信息状态。

## 2. 非目标

当前不以以下目标为优先：

- 收集全互联网最多的 AI 新闻。
- 代替用户完成投资、法律或商业决策。
- 建设企业级新闻数据平台。
- 自动发布未经人工核验的权威新闻。
- 立即构建多 Agent、微服务或多用户 SaaS。

## 3. 核心用户场景

### 场景 A：早上查看昨日完整日报

用户打开首页，立即看到最近一期已经完成的日报。若昨日日报仍在生成，继续展示上一期并显示明确状态。

### 场景 B：白天查看实时采集状态

用户看到今天已经采集多少条、A 级候选数量和信源可用情况，但不会把它误认为今天的最终日报。

### 场景 C：深入阅读和核验

用户打开日报详情，查看重要事件、来源、发布时间和原始链接，并记录已读状态。

### 场景 D：系统失败时继续使用

采集或 AI 失败时，首页仍然打开，旧日报仍可阅读，并告诉用户失败发生在哪里。

## 4. 核心业务规则

1. 项目时区固定为 `Asia/Shanghai`。
2. `today_realtime` 与 `daily_report` 必须是两种不同状态。
3. 最终日报日期等于信息实际发生的自然日。
4. `published_at` 决定归属日期，不能用文件时间或采集时间替代。
5. 今天或未来日期禁止生成最终日报。
6. 同一日期最多只有一个正在执行的结算任务。
7. 采集不因日报存在而停止。
8. 采集阶段原则上不调用 LLM。
9. 日报写入失败不得覆盖已有有效日报。
10. 每条重要事件必须保留来源、发布时间和原始链接。

## 5. 功能优先级

### P0：没有它产品核心价值不存在

| 功能 | 当前状态 | 验收重点 |
|---|---|---|
| 全天采集 | 已实现第一版 | 每 2 小时运行；单源失败不影响其他源 |
| 自然日隔离 | 已实现第一版 | 00:00 边界正确；无跨日污染 |
| 最终日报 | 已实现第一版 | 次日处理昨天；失败不生成空日报 |
| 来源可追溯 | 部分实现 | 重要事件必须有来源、时间和原始链接 |
| 事件去重 | 部分实现 | 同一事件不因多来源重复进入日报 |
| 重要性排序 | 部分实现 | 不是只按热度或发布时间排序 |
| 任务幂等 | 已实现第一版 | 刷新 10 次不产生 10 次 AI 调用 |
| 失败降级 | 已实现第一版 | 首页和旧日报始终可用 |
| 信源覆盖可靠性 | 待加强 | 关键来源可用且发布时间完整 |

### P1：明显提升体验和可信度

| 功能 | 价值 |
|---|---|
| Event 事件层 | 把多篇报道合并为一个真实事件，保留多来源证据 |
| 可解释评分 | 明确 A/B/C、importance_score 和星级的关系 |
| 日报质量评审 | 检查来源一致、时间一致、结构完整和结论越界 |
| 成本与耗时记录 | 知道每天调用次数、耗时和 Token 用量 |
| 连续信源健康趋势 | 区分偶发失败与长期失效 |
| 手动重试和状态反馈 | 用户能理解并控制失败恢复 |

### P2：增强功能

- 日报全文搜索。
- 按模型、工具、Agent、商业、研究分类浏览。
- 多来源交叉验证标记。
- 日报生成完成后的桌面通知。
- 用户对事件的重要/不重要反馈。
- 手机端在桌面版本稳定后的重新打包与同步。

### P3：未来探索

- Research Agent、Editor Agent、Reviewer Agent。
- 个性化信息偏好和用户画像。
- 多模型策略和质量/成本路由。
- 云端多用户和团队协作。
- 面向公开部署的账号、权限、限流和审计。

当前明确“暂时不要做”：微服务、Redis、Kafka、向量数据库、WebSocket、大规模新增信源和全自动多 Agent 编排。

## 6. 功能详细需求

### 6.1 信息采集

输入：公开 RSS、API 或页面。

输出：统一的 Raw News 数据。

要求：

- 保存原始标题、摘要、来源、原始链接和发布时间。
- 记录采集时间和信源健康状态。
- 同一轮和跨轮采集能够去重合并。
- 未知发布时间必须明确为未知，不得伪造。

### 6.2 事件理解

输入：同一自然日内的 Raw News。

输出：Event 候选。

要求：

- 同 URL、标题高度相似和实体/动作相近的报道合并。
- Event 保存所有来源引用，而不是只留下一个链接。
- 保留“为什么合并”的规则或置信度。
- 不确定是否同一事件时宁可保留两个候选，避免错误合并。

### 6.3 重要性评分

输出统一的 `importance_score`（0～100）和解释字段。

维度：时间、来源可信度、影响范围、新颖性、用户价值、行业影响。

程序负责可确定信号；GPT 只负责语义判断，并必须输出结构化理由。详细设计见 [DATA_DESIGN.md](DATA_DESIGN.md)。

### 6.4 日报生成

- 目标日期必须显式传入。
- 只读取该日期已结束窗口的数据。
- 只把高价值 Event 候选发送给模型。
- 最终日报按重要性排序。
- 生成后校验日期、章节、链接和最低完整度。
- 使用临时文件原子替换正式日报。

### 6.5 首页和历史阅读

- 首页默认展示最近一期完成日报。
- 同时显示今天实时池状态，但不称其为最终日报。
- 历史日报按日期倒序且日期唯一。
- 已读 + 未读必须等于全部日报。
- 任何后台任务不得阻塞首页。

## 7. 非功能需求

### 稳定性

- 单个信源失败不会造成整轮失败。
- AI 失败不会破坏历史日报。
- 多进程和多次刷新不会重复结算。

### 成本

- 采集不调用 LLM。
- 一个日期正常情况下只生成一次最终日报。
- 发送给模型的候选数量有上限。

### 安全

- API Key 只从环境变量读取。
- 日志、JSON、Prompt 和 Git 不包含真实 Key。
- 当前局域网 API 不直接暴露公网。

### 可维护性

- 核心数据契约有版本。
- 重要行为有自动测试。
- 文档与代码同步。

## 8. 产品级验收标准

一个版本只有同时满足以下条件才可发布：

- 核心功能实现并实际运行。
- 正常、失败、边界和重复操作测试通过。
- 历史日报未被意外修改。
- 日期隔离和任务锁测试通过。
- 页面、详情和现有 API 回归通过。
- 真实信源或真实 AI 无法验证时明确标记。
- 文档和版本记录已同步。
