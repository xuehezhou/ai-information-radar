# AI 信息雷达开发路线图

> 说明：根目录 `changelog.md` 的 v1.x 是现有工程变更编号；本文 V0.x/V1.0 是产品成熟度路线。两者不要混用。

## 1. 当前产品阶段

当前能力已经超过基础原型，但 Event 数据层、评分一致性和来源完整性仍不成熟，因此产品成熟度判断为：

> V0.3 已完成，V0.4 部分完成，尚未达到可公开部署的 V1.0。

## 2. 版本路线

### V0.1 基础可阅读版本（已完成）

**目标**：可以生成、保存和阅读 AI 日报。

**解决问题**：从无到有建立日报应用。

**用户收益**：在浏览器中阅读按日期保存的 AI 日报。

**技术实现**：Flask、Jinja、Markdown、`data/daily/`。

**验收标准**：首页、详情页、历史日报和启动方式正常。

### V0.2 当天更新闭环第一版（已完成并被后续机制替代）

**目标**：检测当天是否更新，并在后台触发采集与生成。

**解决问题**：用户长期看到旧日报。

**用户收益**：打开应用能够看到更新状态。

**技术实现**：后台线程、日期级保护、失败状态。

**验收标准**：首页不阻塞、刷新不重复调用、失败保留旧日报。

**演进说明**：产品后来改为“全天采集 + 次日结算”，不再把白天临时生成的内容当作完整今日日报。

### V0.3 日期隔离与稳定日报（已完成第一版）

**目标**：每期日报只属于自己的自然日。

**解决问题**：历史日报错误使用最新数据、今天数据混入昨天。

**用户收益**：日报日期可信且历史稳定。

**技术实现**：上海时区、`target_date`、`published_at` 过滤、任务锁、原子写入、00:05 结算。

**验收标准**：跨午夜测试通过；今天不能提前生成最终日报；重建某天不修改其他日期。

### V0.4 事件级去重与来源聚合（当前下一阶段）

**目标**：一件真实事件只在日报出现一次，同时保留多个来源证据。

**解决问题**：多个媒体重复报道、标题改写导致重复、单链接不能反映交叉验证。

**用户收益**：日报更短、更可信，不重复阅读。

**技术实现**：Raw News 与 Event 分层；URL、标题、实体、动作和时间窗口组合去重；保守的合并阈值。

**前置任务**：先补齐关键信源 `published_at`，否则无法安全按日期聚合事件。

**验收标准**：

- 同事件多来源只生成一个 Event。
- Event 保留全部来源链接。
- 不同事件不会因关键词相似被错误合并。
- 合并结果可解释、可测试。

### V0.5 重要性评分 2.0

**目标**：形成稳定、可解释、跨日报可比较的 `importance_score`。

**解决问题**：当前 A/B/C 和模型星级口径不统一。

**用户收益**：知道为什么某条事件排第一、为什么是五星。

**技术实现**：程序规则分 + GPT 语义分；六个维度；结构化评分理由；人工样本校准。

**验收标准**：至少 30 个真实事件样本；重大官方事件召回率高；无关高热内容不能进入前列；同类事件评分稳定。

### V0.6 Research Agent（有条件引入）

**目标**：对少量高价值 Event 补充来源验证和事实证据。

**解决问题**：单一来源或社区传闻难以确认。

**用户收益**：重要事件的事实基础更可靠。

**技术实现**：受控工具、允许的来源范围、证据列表、调用预算和超时；不是无限自主浏览。

**验收标准**：输入输出结构固定；每个结论可回溯证据；失败不阻塞普通日报；成本上限明确。

### V0.7 Editor Agent

**目标**：把已经验证和评分的 Event 编辑成一致、易读的日报。

**解决问题**：日报风格、结构和星级尺度不稳定。

**用户收益**：每天输出质量更一致，更适合快速阅读。

**技术实现**：稳定 Event 输入、固定输出契约、单次主编辑调用。

**验收标准**：固定章节完整；不引入候选外事实；重要事件含来源、时间和链接；成本不高于当前可接受范围。

### V0.8 Reviewer Agent

**目标**：在发布前检查事实引用、日期、重复、遗漏和格式。

**解决问题**：当前质量闸门主要检查结构和链接，难以发现语义矛盾。

**用户收益**：减少看似完整但内容错误的日报。

**技术实现**：优先确定性校验；只有语义检查使用 Reviewer，失败时不发布新日报。

**验收标准**：已知错误样本能够拦截；正常日报误杀率可接受；Reviewer 不能自行修改原始事实。

### V0.9 开源准备版本

**目标**：新电脑可以安全、可复现地运行。

**解决问题**：本机路径、密钥、构建物和运行说明不统一。

**用户收益**：其他开发者能够安装和参与。

**技术实现**：Git 基线、LICENSE、配置检查、示例数据、构建说明、跨环境测试。

**验收标准**：干净环境按 README 启动；仓库无 Secret；测试可重复；源码版和发布版关系明确。

### V1.0 开源可部署版本

**目标**：形成稳定的单用户/小团队部署版本。

**解决问题**：从个人电脑项目升级为可以维护和发布的产品。

**用户收益**：可靠自动运行、可配置、可诊断、可升级。

**技术实现**：模块化单体、版本化数据契约、可靠调度、发布流程和基础安全。

**验收标准**：

- 连续 30 天核心任务成功率达到目标。
- 日期污染和历史覆盖为 0。
- 重要事件来源完整。
- 安装、配置、启动、升级和回滚文档完整。
- 发布前自动测试和真实链路验收通过。

## 3. 最近三轮推荐顺序

1. **发布时间完整性**：为关键官方和开源来源提供可信 `published_at`。
2. **Event 数据层**：把文章变成事件，保留多来源证据。
3. **importance_score 2.0**：统一规则分和模型语义分。

不要跳过前两步直接 Agent 化，因为 Agent 的输入数据如果日期和事件都不稳定，只会更昂贵地生成不稳定结果。

## 4. 每轮发布门槛

- 只解决一个主要问题。
- 明确修改范围和不修改范围。
- 正常、失败、边界和回归测试通过。
- 真实外部链路能测则实际测试，不能测则明确标记。
- 历史日报和已有 API 无意外变化。
- 文档、版本记录和验收方式同步。
