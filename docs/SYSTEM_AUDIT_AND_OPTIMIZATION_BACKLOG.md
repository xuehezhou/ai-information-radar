# AI 信息雷达系统体检与优化 Backlog

> 体检日期：2026-08-31  
> 依据：当前源码、37 项自动测试、运行数据、计划任务、真实采集与真实 AI 日报结算。  
> 原则：文档中写“规划”的能力不等于代码已经实现。

## 1. 结论

当前项目不是新闻 Demo，已经具备“采集 → 规则过滤 → 单次 AI 编辑 → 日报 → Web/API 阅读”的可运行主链路。综合成熟度约为 **58/100**，产品阶段仍是 **V0.3 完成、V0.4 部分完成**。

最大风险不是页面，也不是模型能力，而是自动运行中断后缺少连续恢复。体检时已结束自然日应有 26 期日报，实际只有 17 期；计划任务不存在，且一个任务锁已陈旧数天。Batch 1 因此优先修复“自动运行与日报连续性自愈”。

## 2. 真实业务闭环

```text
公开信源
  -> Source Adapter
  -> collector.py（并发采集、过滤、分类、A/B/C 初筛）
  -> data/realtime/YYYY-MM-DD.json
  -> generate_daily.py（严格日期过滤、候选评分、规则去重）
  -> OpenAI Responses API（一次编辑调用）
  -> 质量闸门
  -> data/daily/YYYY-MM-DD.md
  -> Flask 首页 / 详情页 / 同步 API
```

已经闭环：采集、日报生成、失败保护、历史阅读、已读同步。  
部分闭环：事件去重、重要性判断、任务恢复、运行可观测性。  
尚未闭环：持久化 Article/Event、搜索/RAG、用户反馈、成本统计、Agent 工作流。

## 4. 当前最大 10 个问题

1. 自动任务曾未注册，系统“代码支持自动更新”但实际不会自动运行。
2. 缺失日报只检查昨天，旧缺口不会自动进入恢复队列。
3. 2026-08-22、23、24、30 缺少原始信息池，不能安全伪造历史日报。
4. Source Adapter 有 9 个，但真实采集只有 6 个可用，来源覆盖不稳定。
5. Article 与 Event 没有真正分层，多来源同事件仍可能重复。
6. A/B/C、候选规则分和 1～5 星没有统一解释和校准。
7. AI 调用不记录 Token、成本、请求 ID和精确耗时。
8. API 无分页和版本，`/api/reports` 会一次返回所有全文。
9. 项目没有 Git 仓库，历史数据和代码变更缺少标准版本保护。
10. 搜索、RAG、反馈、Agent 仍是规划，不应对外宣称已经实现。

## 5. P0～P3 优化清单

### P0：必须解决

#### P0-1 自动运行与连续性恢复（Batch 1 已完成）

- **现在的实现**：计划任务只结算昨天，旧缺口和陈旧锁不会形成恢复队列。
- **理想实现**：昨天优先、旧缺口按日期补齐；一次只处理一期；失败限次重试；首页显示连续性。
- **用户收益**：不会在不知情时连续多天看旧日报。
- **工程收益**：任务可恢复、可追踪、不会无限消耗模型。
- **面试价值**：跨进程幂等、持久状态、自愈任务、真实 Windows 调试。
- **成本/风险**：中；需要避免历史数据被错误重采。

#### P0-2 缺失信息池处置

- **现在的实现**：4 个日期没有信息池，无法生成可信日报。
- **理想实现**：未来采集不中断；历史只使用支持时间范围的来源补采，并标注覆盖度。
- **用户收益**：减少断档，同时不把今天新闻伪装成历史新闻。
- **风险**：高；不可用“最新 RSS”伪造历史数据。
- **是否现在做**：先保证未来不再新增断档；历史缺口单独验收。

### P1：下一阶段

#### P1-1 Article 数据契约与 Event 聚合

- 统一 `article_id/source/published_at/collected_at/canonical_url`。
- 将同一真实事件的多篇文章聚合为一个 Event，并保留全部证据链接。
- 用户收益最高：日报少重复、重要事件证据更完整。

#### P1-2 重要性评分统一

- 用来源可信度、新颖性、行业影响、影响范围、热度、时效性和用户价值形成 0～100 分。
- 程序算确定性维度，GPT 只评估少量语义维度。

#### P1-3 AI 成本与质量 Trace

- 每次结算记录模型、候选数、耗时、状态、Token（端点提供时）和错误类型。
- 不记录 API Key 和完整 Prompt。

#### P1-4 稳定 Python 与运行诊断

- 计划任务必须绑定长期 Python，并验证依赖、环境变量、任务状态和日志编码。
- Batch 1 已解决解释器选择和失败假成功；后续增加一键诊断命令。

### P2：后续优化

- API 分页、统一错误结构和 `/api/v1`。
- 历史日报搜索和按类别筛选。
- Git 初始化、CI、发布检查和可复现打包。
- 只在历史 Event 稳定后评估轻量全文搜索或 RAG。
- 局域网同步需要更安全的配对令牌时再实现鉴权。

### P3：暂时不要做

- Redis、Kafka、微服务、Kubernetes。
- 多 Agent 群聊和多模型自动路由。
- 向量数据库和复杂 RAG。
- 多租户、复杂用户系统和大规模推荐。
- 为追求“企业级”把 JSON/Markdown 立即迁移到数据库。

这些能力当前不能解决漏报、重复事件和评分不稳定，反而提高成本与排错难度。

## 7. Batch 1 实施结果

### 修改

- 建立日报连续性视图：完成数、缺失日期、可恢复日期、缺少信息池日期。
- 新增 `--finalize-pending`：昨天优先，其余按最早缺口，每次只处理一期。
- 自动失败最多尝试 4 次，每次至少间隔 15 分钟；手动重试仍可用。
- 陈旧锁可在下一次领取任务时安全回收；同日期仍使用原子文件锁。
- 首页和 `/api/update-status` 显示真实连续性，不再只说“昨天是否完成”。
- 安装脚本失败时返回非零，不再“注册失败却打印成功”。
- 自动排除 Codex 临时 Python 和 WindowsApps，验证 Flask/Markdown 后选择稳定解释器。
- AI 轻微拼错同域名链接时，严格映射回唯一高相似候选原链接；未知链接继续拒绝。

### 真实结果

- 自动测试：37/37 通过。
- 计划任务：两个任务均为 Ready，绑定 `D:\anaconda3\python.exe`。
- 真实采集：成功，9 个信源中 6 个可用，当日信息池累计 27 条。
- 真实 AI：第一次被质量闸门拦截；修复链接归一化后，成功生成 `2026-08-21.md`，7946 字符。
- Web：主页、详情、状态 API、日报 API 均返回 200。
- 当前连续性：26 期应有、18 期完成、8 期缺失；其中 4 期可用已有信息池恢复，4 期缺少信息池。

## 8. 性能与成本变化

- 首页仍然只读本地文件，不等待采集或 AI；实测约 251ms。
- 状态接口实测约 7ms，连续性扫描当前仅几十个日期文件。
- 每个计划任务只生成一期日报，不增加并行 AI 调用。
- 失败自动重试从“可能反复”变为最多 4 次且有 15 分钟冷却。
- 候选上限仍为 24，不增加输入 Token。
- 当前端点未落盘返回 Token usage，因此不能伪造具体节省金额；Batch 3 再补量化。

## 9. 下一批建议

**Optimization Batch 2：Article 数据契约与 Event 事件聚合。**

理由：自动链路稳定后，用户最直接的内容问题是“同一事件是否重复、来源是否完整、发布时间是否可信”。先把文章标准化并聚合为事件，再统一重要性评分；不要跳过数据层直接做 Agent 或 RAG。
