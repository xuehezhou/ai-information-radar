# AI 信息雷达 AI 开发执行计划

> 本文件用于约束后续 AI 智能体如何执行项目迭代。根目录 `AI_DEVELOPMENT_RULES.md` 仍是长期最高项目约束；本文件补充规划、版本和交付流程。

## 1. 每次进入项目先做什么

1. 确认主目录是 `D:\Allclaude\AI信息雷达-便携版`。
2. 阅读根目录 `AI_DEVELOPMENT_RULES.md`。
3. 阅读本文件和当前任务相关的 docs。
4. 检查 Git 状态；如果尚未初始化 Git，明确说明。
5. 只读取与当前任务相关的代码、配置、数据和测试。
6. 确认 8899 运行的是主源码实例，而不是旧 EXE。

## 2. 修改前检查清单

- [ ] 我理解用户本轮唯一目标吗？
- [ ] 这个问题有明确用户收益吗？
- [ ] 当前代码是否已经有可复用实现？
- [ ] 问题属于采集、处理、Event、AI、展示、调度还是配置？
- [ ] 哪些文件必须修改？
- [ ] 哪些功能明确不在本轮范围？
- [ ] 是否影响日期、历史日报、API、手机同步或已读状态？
- [ ] 是否涉及 Prompt、模型、成本或 Secret？
- [ ] 是否存在更简单方案？
- [ ] 如何测试正常、失败、边界和重复操作？
- [ ] 真实外部服务是否可以验证？

无法回答时先分析，不直接修改。

## 3. 当前不可破坏的业务行为

- 今天只维护实时池，不提前生成完整最终日报。
- 次日 00:05 的 `target_date` 永远是昨天。
- 最终日报只使用目标自然日数据。
- `published_at`、`collected_at`、`collect_date`、`report_date` 不得混用。
- 采集不因日报存在而停止。
- 首页不等待采集或 AI。
- 同一日期最多一个结算任务。
- AI 失败不生成空日报、不覆盖历史日报。
- 首页默认展示最近一期完成日报。
- 历史日报、详情页、API、已读状态和手机同步保持兼容。
- 开发和测试修改源码，不修改旧 EXE 代替源码。

## 4. 禁止擅自进行

- 一次性重构整个项目。
- 删除历史日报、实时池或已读数据。
- 用采集时间伪造原始发布时间。
- 为修复失败关闭日期校验、链接校验或任务锁。
- 每次页面刷新都调用 AI。
- 未经说明修改 Prompt、模型 ID、Token 上限或端点。
- 把 API Key 写入代码、文档、日志、JSON 或 Git。
- 新增 Redis、队列、数据库、微服务或 Agent 框架，除非真实问题已证明需要。
- 创建 `_v2`、`_new`、`_backup`、`_copy` 文件。
- 同时开发多个无关高价值任务。

## 5. 每轮实施流程

```text
确认问题和用户收益
  -> 收集当前证据
  -> 定位根因
  -> 设计最小方案
  -> 明确数据流和影响范围
  -> 原地修改必要文件
  -> 增加有价值的测试
  -> 自动测试
  -> 真实环境测试
  -> 回归已有功能
  -> 更新文档和版本记录
  -> 停止并等待下一轮
```

用户已经授权完整任务时，不需要每个小步骤都询问。只有高风险、破坏性操作、核心行为改变或必须扩大范围时才暂停确认。

## 6. 分层测试要求

### 采集层

- 单信源成功、失败、部分成功、空结果。
- 代理失败后直连回退。
- 发布时间解析和上海日期边界。
- 跨轮合并不丢数据。

### Event 和评分层

- 同 URL 去重。
- 同事件多来源合并。
- 相似但不同事件不误合并。
- 无关高热内容不挤占候选。
- 高价值低热官方事件不漏掉。
- 分数范围和解释字段完整。

### AI 层

- Key 缺失、HTTP 错误、超时、空内容和非法结构。
- 输入候选不重复。
- 输出不包含候选外的重要事实链接。
- 失败不覆盖日报。
- 真实调用能测时必须实际验证，不能用 Mock 宣称真实通过。

### 调度层

- 23:59、00:00、00:05、00:06。
- 连续或并发触发 10 次只有一个任务所有者。
- 失败重试不会重复发布。
- 过期锁处理不会误删正在运行的锁。

### 展示和 API

- 首页、详情页、404。
- `/api/reports`、`/api/read`、`/api/update-status`、`/api/update-check`、`/api/instance`。
- 已读 + 未读 = 全部日报。
- 更新中和失败时仍显示最近完成日报。

## 7. 验收标准

完成不等于代码写完。至少满足：

- 功能实际实现。
- 相关自动测试通过。
- 能执行的真实链路已经执行。
- 外部阻塞项明确标记“未实际验证”。
- 历史文件无意外变化。
- 没有新增无关依赖和文件。
- 文档与真实代码一致。
- 用户知道如何自己验收。

## 8. 版本和记录

- 产品成熟度按 [DEVELOPMENT_ROADMAP.md](DEVELOPMENT_ROADMAP.md) 的 V0.x/V1.0 管理。
- 工程变更继续记录在根目录 `changelog.md`，直到项目正式统一版本策略。
- 规划状态同步到 [VERSION_CHANGELOG.md](VERSION_CHANGELOG.md)。
- 一个自然开发节点建议一个明确 Git Commit。
- 推荐 Commit：`feat: ...`、`fix: ...`、`docs: ...`、`test: ...`。
- 当前项目若尚无 Git，下一次代码迭代前应先建立基线，但不得擅自提交敏感数据。

## 9. 重要文档同步规则

| 变化 | 至少更新 |
|---|---|
| 产品范围或优先级 | PRD、Roadmap |
| 数据字段或关系 | DATA_DESIGN、迁移说明 |
| 模块和数据流 | TECH_ARCHITECTURE |
| Agent 职责或调用次数 | AI_AGENT_PLAN |
| 环境变量、启动和调度 | README、运行手册 |
| 版本完成 | VERSION_CHANGELOG、根 changelog |

## 10. 每轮最终报告

必须说明：

1. 本轮完成了什么。
2. 修改了哪些文件，为什么。
3. 使用了什么技术，它解决什么问题。
4. 数据如何流动。
5. 实际执行了哪些测试。
6. 哪些真实链路未验证。
7. 是否影响历史日报、API、手机或 UI。
8. 本轮用户收益。
9. 当前已知风险。
10. 下一轮唯一推荐任务。

## 11. 当前开发顺序

```text
关键信源发布时间完整性
  -> Event 数据层和跨来源去重
  -> importance_score 2.0
  -> 成本与质量可观测性
  -> 有条件 Research Agent
  -> Editor Agent
  -> Reviewer Agent
  -> 开源发布
```

任何看起来高级但不能提升信息及时性、真实性、重要性或稳定性的功能，暂时不要做。
