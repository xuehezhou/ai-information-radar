# AI 信息雷达开发计划

> 基线：v1.15，2026-08-20。路线图按用户收益排序，不按技术复杂度排序。

> 2026-08-31 最新运行体检、P0～P3 和分批执行顺序，以 [SYSTEM_AUDIT_AND_OPTIMIZATION_BACKLOG.md](SYSTEM_AUDIT_AND_OPTIMIZATION_BACKLOG.md) 为准。本文件保留此前信源与评分专项规划。

## 1. 当前阶段判断

项目已经从“能展示日报”进入“提高信息覆盖和判断质量”的阶段。

已经完成：

- 全天每 2 小时采集。
- 次日 00:05 统一结算昨天。
- 日期隔离和跨午夜保护。
- 同日任务锁和失败重试。
- 实时池、日报和已读状态持久化。
- OpenAI Responses API 日报生成。
- 日报输出质量闸门。
- 首页信源健康状态展示。
- 30 个自动化回归测试。

当前最大问题已经不是“页面有没有日报”，而是：

> 关键来源是否真的进入了最终日报，以及评分是否稳定、可解释。

## 2. 排序方法

每个任务按照以下顺序判断：

1. 对用户每天看到的重要信息是否有直接影响。
2. 是否高频发生。
3. 是否会造成漏报、错报或误导。
4. 是否影响项目核心目标。
5. 实现成本和风险是否合理。
6. 是否为后续扩展建立可靠基础。

## 3. 当前优先级

### P0：现在必须解决

#### P0-1 补齐关键信源的发布时间

【问题】GitHub、Product Hunt、Qwen、DeepSeek 可能没有可靠 `published_at`。

【原因】部分页面解析器只提取标题和链接，没有提取发布时间。

【影响】严格日期隔离会把这些内容从最终日报排除，出现“实时池看到了，日报却没有”的情况。

【解决方案】逐个适配器提取可验证发布时间；无法取得时明确标记，不猜日期。增加跨午夜和缺失时间测试。

【预计难度】中。

【预计收益】高，直接减少官方发布和热门开源工具漏报。

【是否影响现有功能】会影响候选覆盖，需要保持日期安全规则不放宽。

#### P0-2 恢复高价值失败信源

【问题】GitHub、Reddit 超时，Product Hunt 返回 403。

【原因】站点访问限制、页面结构和网络链路不同。

【影响】开源工具、社区反馈和新产品覆盖不足。

【解决方案】一次只修一个信源，优先 GitHub；使用公开稳定入口或官方 API，避免引入复杂代理系统。

【预计难度】中。

【预计收益】高。

【是否影响现有功能】不应影响；单信源仍需独立失败。

### P1：下一阶段解决

#### P1-1 建立统一星级标准

【问题】1～5 星由模型自由判断，不够稳定。

【解决方案】定义新颖性、行业影响、影响范围、来源可信度、用户价值和时效性六项标准，再映射到星级；修改 Prompt 前先做历史样本对比。

【收益】用户能理解为什么是五星，跨日报更容易比较。

【风险】Prompt 变化可能改变日报风格，必须单独迭代。

#### P1-2 增加 AI 调用成本和质量记录

【问题】目前缺少统一的候选数、请求耗时、模型、调用结果和 Token 使用记录。

【解决方案】在不记录 API Key 和完整 Prompt 的前提下，记录日期、模型、候选数、耗时、状态及 API 返回的用量字段。

【收益】能判断日报变慢或变贵的原因。

#### P1-3 校准分类和初筛关键词

【问题】关键词规则可能误判，例如没有任何关键词时默认分类为 `model`。

【解决方案】增加 `other` 或明确未分类状态，用真实一周数据建立误判样本，再小步调词。

【收益】减少无关内容进入候选。

### P2：后续优化

- 日报全文搜索与分类筛选。
- 关键事件的多来源交叉验证标记。
- 自动生成后提供桌面通知。
- 开源前的配置、许可证、示例数据和隐私清理。
- 手机端在桌面流程稳定后重新同步和打包。

### P3：暂时不要做

- Agent 化和多模型自动调度。
- Redis、消息队列、微服务和独立数据库集群。
- 用户系统、权限系统和公网 SaaS。
- WebSocket 实时推送。
- 大规模新增信源。
- Docker 和云端部署。

原因：这些工作目前不能直接解决漏报、评分稳定性和来源可信度，反而会提高维护成本。

## 4. 版本路线图

### V1.16：日期可用性和官方来源覆盖

目标：抓到的高价值信息能够安全进入正确日期的最终日报。

主要任务：

- 为 GitHub、Product Hunt、Qwen、DeepSeek 补充发布时间提取。
- 明确未知时间数据的处理和页面提示。
- 增加 23:59、00:00、跨时区测试。
- 验证官方来源不会被日期过滤静默排除。

成功标准：

- 所有进入最终候选的事件都有可解析 `published_at`。
- 任何事件只进入自己的上海自然日。
- 不通过“使用采集时间”伪造发布时间。

### V1.17：信源稳定性

目标：常态下至少 7/9 个信源可用，关键官方和开源信源有明确降级。

主要任务：

- 优先修复 GitHub Trending。
- 再评估 Reddit、Product Hunt 的稳定公开入口。
- 为页面结构变化增加解析测试样本。
- 记录连续失败天数，区分偶发故障和长期失效。

成功标准：

- 单信源失败不影响整体采集。
- 首页状态与 JSON 一致。
- 不使用需要隐藏登录态的抓取方式。

### V1.18：评分一致性与可解释性

目标：用户知道为什么某条信息是 A 级或五星。

主要任务：

- 固化六维重要性标准。
- 建立 20～30 条人工标注样本。
- 对比旧 Prompt 与新规则的排序差异。
- 在不扩大页面结构的前提下保留简短评分理由。

成功标准：

- 同类事件星级尺度基本一致。
- 五星事件必须有高可信来源和广泛影响依据。
- 低热度但重大官方事件不会被漏掉。

### V1.19：成本与运行透明度

目标：知道每天花了多少、慢在哪里、失败在哪里。

主要任务：

- 记录一次结算的候选数、耗时、模型、结果状态和 Token 用量。
- 提供本地诊断汇总，不记录密钥和完整敏感输入。
- 建立日报成功率、信源可用率和重复率指标。

成功标准：

- 可以回答“今天为什么没生成”和“本月大约调用多少次”。
- 不泄露 API Key。

### V2.0：可开源、可复现的桌面版本

目标：其他用户按照文档可以安全安装、配置、运行和测试。

主要任务：

- 初始化 Git 并建立清晰提交历史。
- 完成 LICENSE、配置示例、示例数据和安全扫描。
- 建立可复现的桌面打包流程。
- 明确源码版、桌面版和手机版的发布关系。

成功标准：

- 新电脑按 README 可以启动。
- 仓库不含密钥、私人日志和本机绝对路径。
- 自动测试通过后才能发布。

## 5. 每轮迭代模板

```text
发现问题
  -> 用真实数据确认
  -> 按用户收益排序
  -> 只选择一个问题
  -> 最小修改
  -> 自动测试
  -> 真实环境验收
  -> 记录结果
  -> 等待下一轮确认
```

每轮必须输出：

- 修改了什么。
- 为什么修改。
- 使用了什么技术。
- 数据流发生了什么变化。
- 测试了什么。
- 用户如何自己验收。
- 哪些外部条件未验证。
- 下一轮唯一最高收益任务。

## 6. 当前唯一推荐任务

下一轮只做：

> 补齐关键信源 `published_at`，确保官方发布和热门开源项目可以安全进入所属日期的最终日报。

它优先于继续增加信源，因为“抓到但无法进入日报”比“信源数量少”更直接影响用户价值。
