# AI 信息雷达 Agent 规划

> 结论：当前不应该马上全面 Agent 化。先稳定数据、事件和评分契约，再逐步引入受控 Agent。

## 1. 当前是否需要 Agent

当前系统已经有 AI 调用，但它本质上是一次受约束的日报生成，不是完整 Agent 系统。

目前最紧急的问题是：

- 部分信源失败或缺少可靠发布时间。
- Raw News 尚未形成独立 Event 数据层。
- 重要性分数和模型星级口径不统一。
- 还没有足够的人工样本评估 Agent 是否真的提升质量。

如果现在直接加入多个 Agent，会增加调用次数、Token、延迟和排错难度，却不能自动修复输入数据不可靠的问题。

因此采用：

```text
稳定数据契约
  -> 建立 Event
  -> 统一评分
  -> 单个受控 Agent
  -> 评估收益
  -> 再决定是否增加下一个 Agent
```

## 2. Agent 化的准入条件

只有满足以下条件才开始 V0.6：

- 进入候选的事件都有来源、原始链接和可解析发布时间。
- Event 聚合已有稳定测试。
- `importance_score` 有清晰规则和人工基准样本。
- 当前单次编辑调用的成本、耗时和失败率可统计。
- 能明确说明 Agent 比普通函数或单次 LLM 调用多解决了什么问题。

## 3. Research Agent

### 职责

- 对高价值候选发现补充来源。
- 验证官方发布、时间、主体和关键数字。
- 判断多个报道是否描述同一事件。
- 输出证据列表和不确定性，不直接写最终日报。

### 输入

```json
{
  "event_id": "evt_...",
  "title": "候选事件标题",
  "event_date": "2026-08-19",
  "source_refs": [],
  "questions": []
}
```

### 输出

```json
{
  "verified_facts": [],
  "source_refs": [],
  "confidence": 0.0,
  "uncertainties": [],
  "status": "verified|partial|unverified"
}
```

### 权限边界

- 只读公开网页和允许的 API。
- 不登录用户账户。
- 不写日报、不删除数据、不改变任务状态。
- 不把新发现直接当成事实，必须保留证据 URL。
- 每个 Event 设置来源数、请求数、超时和成本上限。

### 引入时机

V0.6。只处理 importance_score 高于阈值、来源不足或事实存在冲突的少量 Event。

## 4. Editor Agent

### 职责

- 根据已经筛选、评分、验证的 Event 生成日报。
- 统一标题、摘要、排序、影响分析和学习建议。
- 区分事实、推断和建议。

### 输入

只能接收标准 Event，不直接接收所有原始新闻。

### 输出

- 固定 Markdown 结构。
- 每条重要事件引用 `event_id` 和来源。
- 不允许引入输入之外的新事实或链接。

### 引入时机

V0.7。当前 `generate_daily.py` 的单次编辑调用可以逐步演进为 Editor Agent，但不能仅改名就宣称完成 Agent 化。

## 5. Reviewer Agent

### 职责

- 检查日报日期是否正确。
- 检查重要事件是否重复。
- 检查结论是否有来源支持。
- 检查引用链接、发布时间和事件主体是否一致。
- 检查星级和 importance_score 是否明显冲突。

### 不负责

- 不擅自重写整份日报。
- 不改变 Raw News 和 Event 原始事实。
- 不决定文件路径和任务状态。

### 引入时机

V0.8。确定性质量闸门先执行，只有语义问题交给 Reviewer，避免为简单格式校验浪费 Token。

## 6. 推荐工作流

```text
Raw News
  -> 确定性清洗
  -> Event 聚合
  -> 程序基础评分
  -> GPT 语义评分（必要时）
  -> 高价值或冲突事件交给 Research Agent
  -> Editor Agent 生成日报
  -> 程序质量闸门
  -> Reviewer Agent 语义复核（条件触发）
  -> 发布
```

不是每条新闻都走三个 Agent。低价值事件不研究，格式校验不用 Agent，已有高可信官方来源的事件也不必重复研究。

## 7. 成本控制

- 每日主编辑最多一次正常调用。
- Research 只处理少量高价值或有冲突的 Event。
- Reviewer 优先条件触发，而不是每天无条件二次生成。
- 相同 Event 的研究结果按 `event_id + source_version` 缓存到本地文件。
- 记录模型、请求次数、候选数、耗时和用量，不记录 API Key。
- 任何重试都必须有日期锁和幂等保护。

## 8. 失败处理

| 失败点 | 行为 |
|---|---|
| Research 失败 | 标记 `unverified`，不伪造结论；可降低排序或保留不确定提示 |
| Editor 失败 | 不生成空日报，保留上一期日报 |
| 程序质量闸门失败 | 状态 failed，不进入正式文件 |
| Reviewer 失败 | 根据策略保留“待人工复核”，不能擅自判为通过 |

## 9. Agent 验收指标

- 来源核验准确率。
- 重复 Event 降低比例。
- 人工认可的 Top 10 命中率。
- Agent 引入前后日报事实错误率。
- 每日报告调用次数、Token 和总耗时。
- 失败后是否仍能恢复和阅读旧日报。

## 10. 暂时不要做

- 无限循环自主研究。
- 多 Agent 群聊式讨论。
- 让 Agent 自由修改源码、数据或任务状态。
- 给每条 Raw News 都调用模型。
- 在没有评测集前做多模型自动路由。
- 把 Agent 名称当作产品价值，而没有可测量的质量提升。
